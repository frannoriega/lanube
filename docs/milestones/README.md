# Milestones

Forward-looking feature docs, one per milestone. Each doc states the use case,
what needs building, and an implementation plan — not a task-by-task
execution plan (see `docs/superpowers/plans/` for that level of detail once a
milestone is scheduled).

Grouping criterion: one coherent piece of user-facing (or operator-facing)
capability per milestone, regardless of how many files it touches. A
milestone is done when its use case is fully satisfied, not when an arbitrary
task list is checked off.

- [`milestones-1-admin-reservations-browsing.md`](./milestones-1-admin-reservations-browsing.md) — replace the fixed two-week reservation window (dashboard + admin page) with a paginated, arbitrary-window view, and add an "All spaces" filter as the default. **Implemented** on branch `milestone-1`.
- [`milestones-2-audit-trail.md`](./milestones-2-audit-trail.md) — record who did what, with a before/after diff and a human-readable timestamp, across admin mutations. **Implemented** on branch `milestone-2`: every admin route that mutates state writes an entry, cascade attribution works (an approval and the rejections it causes share a `requestId`), and a test walks the route tree so a new uninstrumented mutation fails the build. Upload routes and the 501-stub Incidents API are explicitly exempt.
- [`milestones-3-seasonal-landing-themes.md`](./milestones-3-seasonal-landing-themes.md) — superadmin-configurable date-based landing themes (anniversary/Christmas/etc.), starting with a first-visit "tada" emoji shower. **v1 implemented** on branch `milestone-3` (`LandingTheme` model, `resolveActiveTheme()`, `/admin/themes`, `EmojiShower`, hero eyebrow/keywords override); the effect-trigger question is resolved in the doc. The deferred v2 items (accent presets, top banner/ribbon) stay open in `OPEN_QUESTIONS.md`.
- [`milestones-4-news-section.md`](./milestones-4-news-section.md) — a public "Noticias" section backed by a new `NewsPost` model, a new Comunicador role, and a featured flag. **Implemented** on branch `milestone-4`.
- [`milestones-5-recurring-reservation-cancel-scope.md`](./milestones-5-recurring-reservation-cancel-scope.md) — ask "this occurrence or the whole series?" when a user cancels a recurring reservation. **Implemented** on branch `milestone-5`.
- [`milestones-6-teams-and-organizations.md`](./milestones-6-teams-and-organizations.md) — flat admin-provisioned `Organization`s plus self-service `Team`s as bookable actors. Planning only.
- [`milestones-7-proposals.md`](./milestones-7-proposals.md) — a community suggestion box; the dormant `Proposal`/`ProposalComment` schema gets migrated to match the use case. Planning only.
- [`milestones-8-inventory-and-purchase-orders.md`](./milestones-8-inventory-and-purchase-orders.md) — track equipment and consumables with restock thresholds; restructures the dormant `Inventory`/`PurchaseOrder` schema. Planning only.
- [`milestones-9-dynamic-roles.md`](./milestones-9-dynamic-roles.md) — replace the hardcoded `UserRole` + `rbac.ts` permission map with superadmin-defined roles. **Implemented** on branch `milestone-9` (branched from `preview`): `Role` rows + `RegisteredUser.roleId`, `/admin/roles` CRUD, resolved permissions on the JWT, behaviour-preserving seed. One blocker left open — the Vercel Global Config cache the doc decided on is shipped as a swappable in-process seam instead.
- [`milestones-10-frontend-audit-hardening.md`](./milestones-10-frontend-audit-hardening.md) — findings from the 2026-09-23 frontend audit (error handling, accessibility/contrast in both themes, security headers), sliced into fixes. A **quality** milestone rather than a feature one. **Implemented** on branch `milestone-10` (from `milestone-9`): all six slices, plus a contrast regression test that reads the tokens out of `globals.css`. Two items held back on purpose — the CSP nonce (needs a preview walkthrough) and the auth pages' dark mode (needs a design pass).
- [`milestones-11-ui-navigation-and-consistency.md`](./milestones-11-ui-navigation-and-consistency.md) — navigation and consistency fixes reported from walking the UI: breadcrumbs on every management page (derived from the pathname, so new pages are covered automatically), logo links home everywhere, sign-out lands on sign-in, `/noticias` renamed to `/news` with permanent redirects, the Noticia detail page gains an author strip + "otras noticias" sidebar, landing cards share a height, cover images become required, and the focus ring stops reading as a border. A **quality** milestone. **Implemented** on branch `preview`. Closes milestone-10's auth-page dark-mode item as won't-fix (by instruction).
- [`milestones-12-domain-audit-reservations-and-lifecycle.md`](./milestones-12-domain-audit-reservations-and-lifecycle.md) — hallazgos de la auditoría de dominio del 2026-09-24 y su segunda pasada del 2026-09-25: el `reservation_ledger` no tenía FK, ni propagación de estado, ni predicados de capacidad correctos (así que cancelar una reserva nunca liberaba el lugar, y la disponibilidad se reportaba de menos y de más al mismo tiempo); el cron nocturno borraba el historial de reservas que lee `/admin/reports`; editar un evento o una Noticia publicados podía doble-reservar un espacio o dejar en 404 un link compartido; y la segunda pasada encontró que el baneo no se aplicaba en `/api/**`, que el captcha fallaba abierto sin su clave, y que la tabla `report_snapshots` no existía. Un milestone de **calidad**, contraparte de dominio del milestone 10. **Implementado** en la rama `preview`: ocho slices (A–H), 11 migraciones, 27 de 28 hallazgos corregidos (D21 no se reprodujo). Incluye la política de retención decidida en el proceso: 3 años de historial compactado, 12 meses de detalle crudo, y nunca se borra crudo sin snapshot previo. Este doc y su código están escritos en español.
- [`milestones-13-notifications.md`](./milestones-13-notifications.md) — an abstract notification system (`NotificationEvent` → `notify()` → pluggable `NotificationProvider`s) replacing the pattern of each feature hand-rolling its own nodemailer call. **Implemented** on branch `preview`: in-app (`Notification` model + bell UI in the shared management header) and email channels, wired into reservation approve/reject, event session changes (additive to the existing batched email), and Noticia decisions. Participant-registration emails were deliberately left as their own senders — see the doc's "Not done in this pass".
- [`milestones-14-mobile-redesign.md`](./milestones-14-mobile-redesign.md) — findings from a 2026-10-01 mobile walkthrough (a user-recorded phone session): the booking calendar clips 3 of 5 weekdays entirely on mobile (not just unintuitive — unreachable), six admin config tables overflow the viewport with no scroll wrapper (one of seven, `roles-manager.tsx`, does it right), and the admin reservations timeline scrolls but isn't discoverable. A **quality** milestone. **Implemented (2026-10-02)** — design agreed with the user, then built autonomously item by item (one unsigned commit each on `preview`): nav drawer on `Sheet`, responsive dialog/drawer, 1/3/5-day booking calendar with tap-to-book, `DataTable` cards on phones for every admin list, shared drag-and-drop "Reordenar" mode, sectioned page forms with sticky save bar + unsaved-changes guard, theme and role editors as pages. Conventions in CLAUDE.md §13. Scope extended (Part B) to HTML forms on all viewports: dialog-vs-page rule, sectioned layouts, sticky save bar, drag-and-drop reorder mode replacing numeric order fields, paginated event sessions. The admin reservations Gantt is explicitly out of scope. Deliberately handed off to a design-focused session rather than fixed here; the doc is written as that session's starting brief, including which findings are real bugs vs. confirmed-intentional (the landing page marquees).
- [`milestones-15-news-redesign.md`](./milestones-15-news-redesign.md) — rediseño visual del listado y el detalle de Noticias, manteniendo sus layouts: nota principal a dos columnas, portada generada por slug para notas sin imagen, tarjetas con fecha mono, tiempo de lectura y "Leer →", filtros como píldoras; el detalle se lee como artículo (kicker-ruta, copete con el `summary`, byline con fecha larga, cuerpo con `Markdown size="reading"`, riel compacto numerado y pie "Seguí leyendo"). Un milestone de **diseño**, sin cambios de modelo ni consultas. **Implementado (2026-10-02)** en `preview`, commits sin firmar. Tras la revisión del usuario se agregó un progreso de lectura flotante (porcentaje + minutos restantes, renderizado en un portal porque `fixed` no se anclaba a la ventana dentro del layout público). Compartir y separadores por mes quedaron sin hacer por elección del usuario.
- [`milestones-16-audit-registry-and-admin-lists.md`](./milestones-16-audit-registry-and-admin-lists.md) — la auditoría pasa a un **registro tipado** (`src/lib/audit/registry.ts`: entidades con sus campos y tipos, eventos con su `kind`) y a un "bus" `beginAudit(...).commit(...)` con fotos antes/después, así toda acción muestra un diff legible por tipo de campo (texto largo con diff por palabras, imágenes, fechas, listas, preguntas de formulario) y agregar algo auditable es declararlo en un solo lugar (con tests que avisan si falta una pieza). Además: reordenar dentro de la misma tabla (y la vista "Destacados/as" para eventos y noticias, sin modal), rango anual con calendario para los temas (cruza el fin de año), checkboxes + acciones en lote (cancelar/eliminar, destacar, quitar) en eventos y noticias, y eventos como tabla. El usuario eligió el registro tipado sobre un outbox en base. **Implementado (2026-10-02)** en `preview`.
- [`milestones-17-account-settings-and-passkeys.md`](./milestones-17-account-settings-and-passkeys.md) — la configuración del usuario pasa a **secciones con ruta propia** (Perfil / Identidad / Seguridad / Cuenta); el **DNI y el motivo para unirse dejan de ser editables**: se piden con una solicitud que aprueba o rechaza un admin con el permiso nuevo `users:profile-requests:review` (`/admin/profile-requests`), nunca la propia, auditado; y **passkeys** (WebAuthn con `@simplewebauthn`, alta/renombrar/quitar en Seguridad, "Entrar con passkey" en el ingreso, como segundo proveedor `Credentials` de NextAuth). En una segunda pasada: **códigos de recuperación** (10, de un solo uso, generados con la contraseña, canjeables en el ingreso para poner una contraseña nueva) y **aviso de la decisión** por campana + email. OAuth (ya decidido: pide la contraseña antes de vincular) y cambiar la contraseña en Seguridad quedan postergados. Arregla de paso que la pantalla vieja mostraba "Usuario" como rol para todos. **Implementado (2026-10-02)** en `preview`.
- [`milestones-18-public-brand-experiment.md`](./milestones-18-public-brand-experiment.md) — **experimento** de marca/estilo del sitio público, a partir de un "lo veo muy soso" del usuario: hero con el isologo animado (los nodos llegan volando, destello, se dibuja la nube; una vez por sesión, respeta `prefers-reduced-motion`), azul noche de marca para títulos/franjas/footer y botón `brand`, encabezado de sección compartido, grilla de fotos de espacios, cierre con llamada a la acción, página de evento a dos columnas con ficha e inscripción explícita y sesiones resumidas, `/spaces` con foto+parallax y botón de reservar, leyenda del logo que se dibuja sola, política de privacidad con índice y fecha. De paso: **todas las fechas en español** (`es-AR`, 24 h) y el enlace roto de las tarjetas de espacios. Las tres filas de logos se mantienen por requerimiento. **Implementado (2026-10-02)** en la rama `experimental`, sin mergear: el doc lista lo que hay que decidir antes. Nació como milestone 17 y se renumeró al rebasar sobre `preview` (2026-10-03); en esa revisión las cifras salieron de la landing (son de la ciudad, no de La Nube) y la barra pública ganó un canto de vidrio al hacer scroll.
- [`milestones-19-policies-and-acceptance.md`](./milestones-19-policies-and-acceptance.md) — políticas versionadas: el **texto queda en código** (una versión publicada es un archivo MDX inmutable, con su hash verificado por un test, en un registro tipado con `effectiveAt`, `requiresAcceptance` y si el cambio exige re-aceptar) y las **aceptaciones van a la base** (append-only, con hash, IP y user-agent). Checkbox por política en el registro, y un **gate** "Actualizamos nuestras políticas" que frena `/user`, `/admin` y la API (403 `POLICIES_PENDING`) hasta aceptar, calculado en el `jwt()` como el baneo. Al desplegar, todos los usuarios existentes aceptan por primera vez. **Implementado (2026-10-04)** en `preview`: además del diseño, el gate se repite en los layouts de `/user` y `/admin` (la cookie del JWT puede estar atrasada), tres rutas de usuario que se salteaban el guard pasaron a usarlo (con un test que lo exige), y se encontró que la política publicada mostraba el correo de contacto vacío desde septiembre (un `import` roto en el MDX): ahora los textos son autocontenidos y un test lo exige. Incluye el procedimiento para publicar una versión nueva.
- [`milestones-20-mcp-connector.md`](./milestones-20-mcp-connector.md) — endpoint MCP (`/api/mcp`, revisión 2026-07-28, sin estado) para que cada usuario conecte su asistente (Claude, ChatGPT) y pida o cancele reservas; La Nube pasa a ser un servidor OAuth 2.1 mínimo (PKCE, CIMD + DCR, consentimiento, "Asistentes de IA" en Seguridad). **Implementado (2026-10-04)** en `preview` (slices 1–5): es **una ruta más de la app, no otro servidor** — funciona igual en Vercel gratuito y en un VPS (el doc explica por qué); las reglas de reserva pasaron a funciones de dominio compartidas con la web; el ingreso respeta `callbackUrl`; cinco tools (espacios, horarios libres, mis reservas, pedir, cancelar) con las mismas reglas y mensajes que la web; reservas marcadas «Vía asistente» para el admin; cambiar la contraseña desconecta los asistentes. Falta probarlo con Claude web/ChatGPT contra un deploy público (slice 6).
- [`milestones-21-mcp-management.md`](./milestones-21-mcp-management.md) — el conector MCP llega a la gestión: quien tiene permisos (no un rol: el **permiso** de cada pantalla) consulta **solo lectura** eventos, inscriptos, formularios, solicitudes de cambio de datos, reportes y recursos, y en Noticias lee, revisa (opina en el chat; decidir sigue en el panel) y **redacta borradores** con vista previa y confirmación explícita — nunca publica: devuelve el link al borrador. Todos leen contacto, políticas y "Quiénes somos" (cuyo texto pasó a datos, compartido con la página). Auditoría, tipos de reserva, espacios, contacto (edición), roles y temas quedan **fuera por diseño**, con un test que lo exige. Scopes nuevos `management:read` / `news:write`, ofrecidos solo a cuentas con gestión. **Implementado (2026-10-04)** en `preview`.
